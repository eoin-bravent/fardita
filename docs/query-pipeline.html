FARDITA · Query Orchestration · v0.1

Regulatory RAG Query Pipeline

A modular, typed pipeline for answering FAR/DFARS questions from authorized source material. Stages are intended to use stable contract boundaries; marked strategy slots show where the implementation can be swapped while keeping the same required input and output contract. Each stage shows its input references and one populated example of the object it produces.

swappable implementation same required output contract; implementation can change required control must always run must pass answer cannot continue unless it succeeds model call invokes the LLM/model uses memory provider provider-backed conversation state runs in parallel concurrent fan-out initial scope simplified behavior for the first build
Proposed stage contract pattern
Every stage takes StageInput<T> = PipelineContext + typed payload, and returns StageResult<T> = typed output + trace (stage, version, latency, input/output counts, decision) + warnings + errors. The cards below show only the typed payload — the wrapper and trace are identical for every stage, and the traces feed the audit log and evaluation set.

A swappable implementation tag does not mean the stage can disappear or return a different shape. The stage keeps a fixed responsibility and output contract while its internals change — the reranker, for instance, can start as a no-op and later become a cross-encoder or LLM reranker, but it must still return a ranked candidate set.

Any required control or must pass stage can fail closed by returning a typed fallback such as insufficient_evidence, blocked, clarification_required, or manual_fallback.

The object examples are representative contract sketches, not final API schemas: the stable decisions are the stage boundaries, required controls, and data-flow responsibilities; exact field names and validation rules remain subject to implementation review. Conversation and memory behavior is described on the stages that own it (2, 4, 21).

Interprets the question — citations, terms, current-vs-historical intent, and whether the turn is a follow-up — then rewrites it as a standalone query and chooses how to handle it. If the corpus wasn't pre-set it's detected here; if too ambiguous to answer safely, it asks the user to clarify. Safety is layered: route-level policy can still block, clarify, or restrict the retrieval plan after normalization (say, a request that resolves to restricted historical content). QueryAnalysis is a convenience wrapper for the diagram — implementations may keep NormalizedQuery and RouteDecision as separate typed objects.

Generates one or more search queries from the question using whichever rewrite algorithms the plan enabled — rephrasing (expansion), hypothetical-answer (HyDE), step-back, decomposition, and others; new ones plug in here as strategies. Separately, each derived query carries a fan_in flag for how its results are recombined — merged into one ranked pool, or kept apart and composed into a multi-part answer — which is a different axis from which algorithm produced it. v0.1 enables expansion only, run deterministically; model-assisted rewriting can be added later.
